# Sci Viz Case Hub 公共只读部署与 OSS 迁移设计

日期：2026-07-06  
状态：待外部专业评审  
范围：仅 Sci Viz Case Hub；不包含 Sci AI Studio 部署

## 1. 评审目的

本文用于咨询云部署、后端安全或运维专业人士，确认以下方案是否适合把 Sci Viz Case Hub 作为阶段性的公共只读案例库上线：

- 任何获得网址的人均可免登录查看全部案例；
- 访客可以搜索、筛选、查看案例详情、统计和比较；
- 访客不能新增、修改、删除数据，也不能触发采集、爬虫、OCR、AI 分析或批处理；
- 管理员登录后继续使用现有完整后台；
- 本地历史图片迁移至阿里云 OSS；
- 在不过度建设安全系统的前提下，完成基本的权限隔离、密钥保护、备份和费用控制。

## 2. 当前系统现状

### 2.1 技术组成

- 前端：React + Vite；
- 后端：Node.js + Express；
- ORM：Prisma；
- 数据库：SQLite；
- 图片存储：服务器本地目录；
- 认证：用户名、密码、JWT HttpOnly Cookie；
- 部署：已有多阶段 Dockerfile，可由同一个 Node 容器提供 API、前端静态文件和本地图片；
- 对象存储：已有 `ali-oss` 接入代码，新图片可同时写入本地和 OSS，接口返回时可将 `/uploads/...` 映射为 OSS 公共 URL。

### 2.2 当前数据规模

截至 2026-07-06 的本地统计：

- 案例记录：6,147 条；
- SQLite 数据库：约 23 MB；
- 本地图片案例：4,599 条；
- `server/uploads`：约 2.6 GB；
- 原图：约 2.5 GB；
- 缩略图：约 88 MB；
- 图片文件总数：约 12,186 个；
- 带远程原始图片 URL 的案例：5,996 条。

这些数字是部署设计时的快照，实际迁移前应重新统计。

### 2.3 当前安全边界

目前除健康检查、认证接口和 Studio 对接接口外，大部分 `/api` 路由统一要求登录。现有用户没有角色字段，所有登录用户实际上都拥有同一套后台能力。注册接口目前公开存在，因此当前实现不适合直接暴露到互联网。

现有 OSS 支持尚不构成完整历史迁移方案：

- 新图片保存时会尝试上传原图和缩略图；
- 上传失败目前可能被静默忽略；
- 配置 OSS 凭证后，本地图片路径会映射为 OSS URL；
- 尚无完整的历史文件批量上传、断点续传、逐文件校验和迁移报告工具；
- Docker 部署不会自动包含被 Git 忽略的 2.6 GB 图片，空服务器启动后不能仅依靠当前镜像恢复历史图片。

## 3. 目标与非目标

### 3.1 目标

1. Guest 免登录只读访问全部 6,147 条案例，不按审核状态限制。
2. Guest 可查看现有案例详情字段，包括 OCR、AI 结果、内部备注和处理状态；产品方接受这些内容公开。
3. Guest 无法通过 UI 或直接构造 HTTP 请求改变系统状态。
4. Admin 继续登录并使用现有管理功能。
5. 历史原图和缩略图可重复、可校验地迁移至 OSS。
6. 新采集图片的 OSS 写入失败必须可见、可重试。
7. 具备基本 HTTPS、限流、日志、备份、费用告警和密钥管理。

### 3.2 非目标

- 不实现访客注册、个人账号或收藏；
- 不实现多租户；
- 不阻止访客截图或下载已经展示的图片；
- 不承诺图片内容具备强保密性；
- 不在本阶段迁移至 PostgreSQL；
- 不在本阶段部署 Sci AI Studio；
- 不进行企业级 WAF、零信任或高可用集群建设。

## 4. 方案比较

### 4.1 方案 A：独立公共只读 API（推荐）

新增明确的 `/api/public/...` 路由，只提供白名单查询能力；原 `/api/...` 管理接口继续要求 Admin 登录。

优点：

- 权限边界清晰；
- 不会因为某个管理接口使用 GET 方法而被错误开放；
- 可独立设置缓存、限流和返回字段；
- 后续关闭公共访问时容易整体停用。

缺点：

- 需要复用或抽取案例查询、统计和比较服务；
- 需要调整前端，使未登录状态调用公共 API。

### 4.2 方案 B：所有 GET 请求公开

认证中间件只保护 POST、PUT、PATCH 和 DELETE。

优点是改造较少。缺点是容易把管理查询、任务状态、内部诊断或未来新增的 GET 接口意外公开。本文不建议采用。

### 4.3 方案 C：静态导出网站

定期把案例和统计导出为静态 JSON/HTML。

它的运行时攻击面最小，但筛选、详情、统计更新和数据同步更复杂，每次更新都需要重新构建。考虑到当前后台仍会继续维护数据，本文暂不采用。

## 5. 推荐架构

```text
Internet
   |
HTTPS domain
   |
Nginx / managed ingress
   |
Case Hub container
   |-- React production assets
   |-- /api/public/*      anonymous read-only
   |-- /api/auth/*        admin login/logout/check
   |-- /api/*             authenticated admin only
   |
SQLite persistent volume

Browser ----------------------> OSS/CDN
               thumbnails and originals
```

建议将 ECS、OSS 放在同一阿里云区域。只对公网开放 80/443；Node 服务端口仅供反向代理访问。SQLite 文件放在持久卷，并执行自动备份。

## 6. Guest 与 Admin 权限设计

### 6.1 Guest

Guest 不创建数据库用户，也不签发 JWT。未登录用户访问站点时直接进入只读界面。

允许：

- 浏览案例列表；
- 分页、搜索和筛选；
- 查看案例详情和来源链接；
- 查看全部现有展示字段；
- 查看 Insights 统计；
- 查看来源、学科及三轴比较。

禁止：

- 新增、编辑、删除案例；
- 上传图片；
- 修改审核状态、评分和人工备注；
- 启动爬虫、URL Pool、批处理；
- 调用 OCR、AI 分类或补采；
- 创建或修改 CrawlSource；
- 注册账号；
- 访问管理员用户和系统配置。

### 6.2 Admin

Admin 继续使用现有账号和 JWT Cookie。生产环境应关闭公开注册；管理员账号通过部署命令、一次性初始化或受保护接口创建。

Cookie 最低要求：

- `httpOnly: true`；
- `secure: true`；
- `sameSite: lax`；
- 限定合理的有效期；
- 使用生产环境独立的强随机 `JWT_SECRET`。

### 6.3 服务端强制边界

UI 隐藏不作为权限控制。服务端采用显式白名单公共路由：

- `/api/public/cases`；
- `/api/public/cases/:id`；
- `/api/public/filters`；
- `/api/public/insights/...`；
- `/api/public/comparison/...`。

所有管理路由仍经过认证中间件。公共路由不允许根据请求参数转发到任意内部方法，也不能执行写入或后台任务。

## 7. 前端行为

启动时检查管理员登录状态：

- 未登录：显示 Guest 导航和只读页面；
- 已登录：显示现有 Admin 导航及管理操作；
- Guest 页面保留管理员登录入口；
- 退出登录后回到 Guest 页面，而不是显示无法访问的登录墙。

Guest 隐藏所有采集、审核、处理和删除入口，但服务端权限仍是最终保障。

## 8. OSS 历史图片迁移

### 8.1 对象路径

保持数据库现有路径语义，不逐条重写记录：

```text
server/uploads/originals/<filename>
  -> oss://<bucket>/originals/<filename>

server/uploads/thumbnails/<filename>
  -> oss://<bucket>/thumbnails/<filename>
```

API 返回数据时，将 `/uploads/originals/...` 和 `/uploads/thumbnails/...` 映射为配置的 OSS/CDN 基础 URL。

建议新增 `OSS_PUBLIC_BASE_URL`，避免 URL 生成逻辑与 AccessKey 是否存在绑定，并支持以后切换自定义域名或 CDN。

### 8.2 迁移命令要求

新增独立、可重复执行的 CLI：

1. 扫描 `originals` 和 `thumbnails`；
2. 规范化对象 Key，拒绝目录穿越；
3. 使用小规模并发上传，例如 4～8；
4. 上传前通过 HEAD 检查对象是否已存在；
5. 已存在且大小一致则跳过；
6. 不一致则报告冲突，不默认覆盖；
7. 上传后校验对象大小；
8. 记录 uploaded、skipped、failed、conflict；
9. 输出 JSON 和 Markdown 迁移报告；
10. 失败后可重复执行，实现断点续传；
11. 提供 `--dry-run`；
12. 迁移过程不删除本地文件。

正式切换前应核对：

- 本地文件总数；
- OSS 对象总数；
- 原图与缩略图分类数量；
- 失败和冲突数量为零；
- 抽样检查图片能正常显示；
- 数据库中引用的本地路径是否均有对应对象；
- 本地孤儿文件和数据库缺失文件分别输出清单。

### 8.3 新图片写入

当前实现的 OSS 上传失败会被忽略，建议改为可观测状态：

- 本地保存成功后上传 OSS；
- OSS 失败时记录结构化日志和错误状态；
- 支持后台重试或补传命令；
- 在管理后台或健康检查中显示待同步数量；
- 不应向用户谎报“完整成功”。

部署初期保留本地持久卷副本，确认 OSS 稳定后再决定是否取消服务器原图持久化。

## 9. OSS 权限与流量控制

由于 Case Hub 是免登录公共站点，访客看到的图片最终可以被下载或截图，系统不追求图片强保密。

候选方式：

1. 公共读、禁止公共写，并配置 Referer 防盗链；实现简单，适合阶段性展示。
2. 私有 Bucket + CDN/签名 URL；控制更强，但缓存、URL 过期和开发复杂度更高。

当前推荐第一种，但必须满足：

- Bucket 和对象绝不允许匿名写；
- AccessKey 只属于受限 RAM 用户；
- RAM 权限只覆盖指定 Bucket/前缀；
- AccessKey 仅放服务器环境变量；
- 配置 Referer 白名单，并评估是否允许空 Referer；
- 开启存储、请求、外网流量和费用告警；
- 记录访问统计；
- 列表只加载缩略图，原图仅在详情页加载；
- 图片启用懒加载；
- 对带哈希的不可变文件配置长期缓存。

需要专业评审重点确认：公共读 + Referer 防盗链是否适合目标访问方式，是否应从第一天就使用 CDN 或私有 Bucket。

## 10. 数据库与备份

当前 23 MB SQLite 足以支撑小规模只读访问，短期不必为部署而迁移数据库。

要求：

- SQLite 位于 Docker 持久卷；
- 每日生成一致性备份；
- 备份保存到独立 OSS 私有前缀或另一存储位置；
- 设置备份保留周期；
- 上线前完成一次恢复演练；
- 管理员执行批量操作前创建额外快照；
- 监控磁盘空间；
- 确保单实例写入，避免多个容器同时写同一个 SQLite。

若未来出现多实例、高并发写入或持续公共服务，再考虑迁移 PostgreSQL。

## 11. 基础安全要求

- GitHub 仓库保持 Private；
- 检查 Git 历史是否曾提交密钥，疑似暴露的密钥全部轮换；
- `.env`、SQLite、上传文件不进入 Git；
- 关闭公开注册；
- 使用 HTTPS；
- 安全组只开放必要端口；
- Node、SQLite 不直接暴露公网；
- SSH 使用密钥，限制来源 IP；
- 为公共 API 和登录接口设置不同限流；
- 限制请求体大小；
- 设置安全响应头；
- CORS 仅允许正式域名和必要的管理来源；
- 生产日志不输出密码、JWT、AccessKey 或完整敏感请求；
- 生产错误响应不返回堆栈；
- 设置 CPU、内存、磁盘、5xx 和流量告警；
- 评估案例图片公开展示的版权和来源标注；
- 如不希望搜索引擎收录，增加 `noindex,nofollow` 和 `robots.txt`，但不将其视为访问控制。

## 12. 测试与验收

### 12.1 权限测试

- 未登录可以打开列表、详情、统计和比较；
- 未登录对所有写接口发请求均返回 401/403；
- 未登录不能注册；
- Admin 可以登录并执行原有管理操作；
- Admin 退出后立即恢复 Guest 权限；
- 修改 HTTP 方法、伪造 Cookie、直接调用隐藏接口均不能绕过权限。

### 12.2 数据测试

- Guest 可查询全部案例；
- 搜索、筛选、分页结果与 Admin 只读结果一致；
- 三轴字段口径保持 `functionalPurpose`、`distributionMedium`、`technicalMethod`；
- 统计和比较不把旧 `mediaType`、内容类型或采集方式误作三轴结论；
- 远程图片失效时有回退或占位图；
- 列表不误加载原图。

### 12.3 OSS 测试

- dry-run 不产生写入；
- 中断后可继续上传；
- 重复执行不会重复上传；
- 冲突对象不会被静默覆盖；
- OSS 故障不会导致错误的成功状态；
- 随机抽样原图和缩略图；
- 使用真实域名验证 CORS、Referer、缓存和 HTTPS；
- 模拟一定量并发浏览，检查流量、延迟和费用指标。

### 12.4 部署验收

- 生产镜像不包含 `.env`、数据库和 AccessKey；
- 重启容器后数据库仍存在；
- 恢复备份后系统可用；
- 只有 80/443 可从公网访问；
- HTTP 自动跳转 HTTPS；
- 健康检查不泄露配置；
- 日志中无秘密值。

## 13. 推荐实施顺序

1. 冻结并备份现有 SQLite 与图片目录；
2. 建立 `/api/public` 明确白名单；
3. 关闭公开注册并强化 Admin Cookie；
4. 改造前端 Guest/Admin 双模式；
5. 完成权限自动化测试；
6. 创建 OSS Bucket、RAM 用户、告警和防盗链；
7. 实现 OSS dry-run、迁移、校验和报告；
8. 执行真实历史迁移，但保留本地副本；
9. 修复新图片 OSS 同步的错误可观测与重试；
10. 完善 Docker、持久卷、Nginx 和 HTTPS；
11. 部署测试环境并进行完整验收；
12. 小范围邀请访问，观察一周；
13. 根据流量决定是否接入 CDN 或购买资源包。

## 14. 需要专业人士回答的问题

1. 公开只读 API 与现有管理 API 分离是否足够，是否建议进一步拆成两个进程或两个子域名？
2. 对约 6,000 条案例、2.6 GB 图片和小规模同学访问，SQLite 单实例是否合理？
3. 公共读 OSS + Referer 防盗链是否合适，还是应使用私有 Bucket、CDN 鉴权或签名 URL？
4. 阿里云同区域 ECS、OSS 和 CDN 的组合如何配置，才能避免不必要的公网回源费用？
5. 是否应该从第一天接入 CDN？预估访问量达到什么水平才值得接入？
6. 迁移时仅校验文件大小是否足够，是否应保存并校验 ETag、MD5 或自定义 SHA-256 元数据？
7. OSS 历史迁移并发设置为 4～8 是否合理，是否需要使用 `ossutil` 代替应用内脚本？
8. 当前“本地落盘后异步上传 OSS”的新图片策略是否合理，还是应以 OSS 为主存储？
9. SQLite 一致性备份适合使用 Prisma 停写快照、SQLite backup API，还是其他方案？
10. 当前项目作为阶段性公共展示，最低限度还缺哪些安全响应头、限流、审计或告警？
11. 如果域名和服务器位于中国大陆，备案、内容合规和版权声明需要哪些准备？
12. 是否建议把管理员后台限制为特定 IP、独立子域名、VPN 或 Cloudflare Access？
