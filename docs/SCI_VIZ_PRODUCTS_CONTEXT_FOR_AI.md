## 0. 给新 AI 的一分钟摘要

“科研影像”不是一个普通图库项目，而是一套围绕科研视觉生产建立的双产品系统：

1. **Sci-Viz Case Hub** 是研究基础设施和案例知识库。它负责从高校、科研机构、期刊、企业等来源采集科研视觉案例，保存来源与图像，进行 OCR、AI 分类、人工复核、评分、三轴编码、统计与跨来源对比。它回答的是：**别人如何呈现科研？有哪些可复用的视觉模式和证据？**
2. **Sci AI Studio** 是面向真实项目的科研静图拍摄策划工作台。它接收用户的论文、项目资料、网页、已有照片和目标，由四个可见的 AI 工作角色完成资料诊断、科学审校、案例对标、视觉策展和摄影方案生成，并把结果变成可编辑、可审核、可执行的画面卡与现场清单。它回答的是：**这个科研团队下一次具体应该拍什么、为什么拍、怎么拍？**

两者的关系是：

```text
公开世界中的科研视觉案例
        ↓ 采集、分类、复核、研究
Sci-Viz Case Hub（证据库 / 参照系 / 研究引擎）
        ↓ 受保护的只读推荐 API
Sci AI Studio（项目理解 / 策展决策 / 拍摄策划 / 协作执行）
        ↓
可沟通、可审校、可执行的科研静图方案
```

关键边界：Studio **不直连** Case Hub 的 SQLite，也不依赖其内部数据库结构；Case Hub 只通过服务间密钥保护的只读接口向 Studio 提供案例推荐。两个产品可以独立运行。

## 1. 总体愿景与核心问题

科研团队普遍拥有大量研究成果、设备、实验过程和人员故事，但视觉表达往往存在几类断层：

- 研究内容复杂，摄影或宣传团队无法在短时间内理解“真正重要的是什么”。
- 现有影像常停留在会议照、合影、设备记录，缺乏尺度、过程、细节、应用和叙事。
- 优秀案例散落在期刊、大学、实验室、企业研发和新闻网站中，难以系统检索、比较和复用。
- 科研人员、策划者和摄影师之间缺少同一套可讨论的视觉语言。
- AI 可以生成文字，却容易脱离来源、编造科研事实，或给出无法在现场执行的泛化建议。

本项目试图建立一条从“观察世界”到“指导生产”的链路：

```text
案例采集 → 视觉编码 → 风格与用途研究 → 项目资料理解
→ 案例对标 → 科学审校 → 视觉策略 → 画面设计 → 现场执行
```

最终价值不是“更多图片”或“更多 AI 文案”，而是把科研视觉经验转化为：

- 可追溯的研究证据；
- 可比较的视觉分类与谱系；
- 可解释的策略判断；
- 可执行的拍摄动作；
- 可积累的方法论资产。

这不是“Case Hub 加一个 AI 页面”，也不是“Studio 内置一份案例 Fixture”这么简单。长期产品逻辑是：**Case Hub 建立公共参照系，Studio 把参照系应用到私有项目决策中。**

# 第一部分：Sci-Viz Case Hub

## 3. 产品定位

Sci-Viz Case Hub 是一个科研视觉案例自动收集、分类、复核、分析与沉淀工具。它服务于科研影像工作室的前期调研、视觉基准分析、风格谱系构建、案例拆解、视觉策略制定和方法论沉淀。

它不是：

- 普通图片收藏夹；
- 只收摄影作品的图库；
- 无边界全网爬虫；
- 只看“好不好看”的灵感墙；
- 用未经复核的 AI 标签直接得出结论的黑箱分析工具。

它要把零散网页视觉材料转化为“有图、有来源、有上下文、有编码、有状态、有判断”的结构化案例。

## 4. 案例范围

案例库采用广义“科研视觉表达”定义，覆盖：

- 实验室、科研人员、设备、实验过程与现场摄影；
- 显微、电子显微、MRI、CT、遥感、热成像等科学成像；
- 论文机制图、流程图、结构图、科学插画；
- 数据图表、数据可视化和仪表盘；
- 3D 渲染、模拟、分子或工程结构可视化；
- 期刊封面、Graphical Abstract、科普图解、新闻传播图；
- 图组、动图、视频、交互式视觉与实体传播物的记录；
- 高校、研究机构、企业研发、解决方案与产业转化语境中的视觉表达。

因此，Case Hub 的研究对象不是单一“摄影风格”，而是科研内容在不同功能、媒介、技术、学科、机构和传播目标中的视觉呈现方式。

## 5. 核心业务流程

```text
来源规划
→ URL / 浏览器插件 / 本地文件 / 定向爬虫采集
→ 保存原图或媒体副本与缩略图
→ 感知哈希去重与候选质量过滤
→ OCR / 图像理解 / AI 初步分类
→ 待复核工作台
→ 人工批准、拒绝、改标、评分、备注
→ 入库分析
→ 分布、交叉矩阵、跨来源对比与报告导出
```

关键原则：远程 URL 不是可靠资产，重要图像应保存本地或对象存储副本；数据库保存结构化元数据，而不是把大文件塞进数据库。

## 6. 三轴分类体系：长期分析的核心口径

三轴回答三个互相独立的问题：

| 维度 | 字段 | 问题 | 主类 |
| --- | --- | --- | --- |
| 功能维度 | `functionalPurpose` | 影像为什么存在、用来做什么？ | 记录、解释、数据、展示、传播、交互 |
| 媒介维度 | `distributionMedium` | 影像以什么形式被观看和传播？ | 静图、动图、视频、图组、交互、实体 |
| 技术维度 | `technicalMethod` | 影像通过什么方式生产？ | 拍摄、成像、绘设、数据、渲染、生成 |

三轴允许组合。例如“一张面向公众传播的电子显微镜图”可以是：

```text
功能 = 传播
媒介 = 静图
技术 = 成像
```

### 6.1 三轴边界

- `mediaType` 是旧呈现方式字段，混合技术、风格和媒介线索，只能辅助筛选或迁移，不能替代三轴。
- `contentType` 描述内容对象或题材，不属于三轴。
- `discipline` 是学科分层，不属于三轴。
- `mediaSubType`、`contentSubType` 是细分检索线索，不应被误写成三轴主类。
- `captureType`、`检索补采`、`浏览器截图` 等是采集或处理方式，不是视觉生产技术。
- 案例在网页中以截图保存，不代表其技术维度是“截图”。
- 长期报告优先使用已复核案例；AI 补标结果要经过抽检，不能把高覆盖率等同于高准确率。

## 7. 案例数据模型

核心实体 `VisualCase` 大致包含六组信息：

1. **身份与来源**：标题、来源 URL、来源域名、页面标题、案例标题。
2. **媒体资产**：原始图片 URL、本地路径、缩略图、感知哈希；另预留视频 URL、平台和时长。
3. **采集上下文**：页面上下文、OCR、采集类型、用户提示、采集质量分和理由。
4. **视觉编码**：旧字段 `mediaType`、`contentType`、`discipline`，三轴字段，子类型，构图、色调、用途等。
5. **AI 分析**：摘要、可借鉴点、风险提示、置信度。
6. **人工治理**：复核状态、星级、人工备注、创建与更新时间。

其他关键实体：

- `CrawlSource`：采集来源、类型、适配器、爬取层级、状态、价值判断和策略提示。
- `CrawlJob`：一次来源爬取任务的发现 URL、进度、新增数量和错误。
- `CollectionKpi`：按维度和类别配置采集目标、优先级与覆盖缺口。
- `User`：Case Hub 内部后台的简单登录用户。

## 8. 采集系统

Case Hub 同时支持人工、半自动与批量采集：

- Chrome 扩展：右键保存网页图片、选中文字、页面截图和页面图片。
- 单个捕获 API：上传图片、URL 或媒体信息。
- 指定 URL 抓取：发现页面图片、结合上下文过滤 logo、icon、广告和小图。
- 来源池：管理 CrawlSource、诊断可抓取性和适配器需求。
- 静态站点适配器：针对高校、实验室、期刊或机构页面结构定制。
- 浏览器渲染补采：处理动态渲染、反爬或静态 HTML 不足的页面。
- 定向批次脚本：国内高校、国际高校、企业、医学环境、工程、NOAA、SJTU 平台等。

来源组目前重点包括：

- 上海交通大学院系、实验室与校级新闻；
- 国内高校，包括清华、北大、浙大、哈工大、华科、北航、西交、东南、北理工等；
- 国际大学、研究机构、期刊和科学组织；
- 企业研发、技术、案例、解决方案、产品与行业页面。

企业组不是普通品牌广告图库，而被定义为“**商业化科研视觉呈现基准**”，重点观察应用场景、产品或解决方案绑定、性能结果、品牌叙事、行业受众和商业转化路径。

## 9. OCR、AI 分析与数据治理

Case Hub 支持：

- OCR 提取图中文字；
- 视觉模型判断图像内容并生成摘要；
- 自动建议旧分类字段与三轴字段；
- 识别可借鉴点与风险；
- 感知哈希查重；
- 对失败任务进行恢复或重分析；
- 批量补标、标签归一化与覆盖审计。

AI 的角色是“提高整理速度”，不是替代研究判断。人工复核工作台负责：批准、拒绝、修改标签、评分、备注、发现误采与纠正 AI 偏差。

典型复核状态包括 `pending_ai_analysis`、`approved`、`needs_review`、`rejected` 等。具体统计应查询实时数据库。

## 10. 分析能力

Case Hub 不止提供案例浏览，还提供研究工具：

- 多字段分布统计；
- 学科、来源、机构、企业、复核状态等过滤；
- 任意维度交叉矩阵；
- 三轴或子类型频谱；
- 交大院系与国内、国际、企业参照组对比；
- 平衡抽样与实时样本模式；
- 企业商业化视觉信号分析；
- 代表案例缩略图与原始来源回链；
- 统计报告和导出。

跨源对比的核心不是简单比较图片数量，而是回答：

- 不同机构偏向记录、解释、数据、展示还是传播？
- 它们主要使用拍摄、科学成像、绘设、数据可视化、渲染还是生成？
- 某学科或院系与国内同行、国际机构、企业研发的视觉差距是什么？
- 哪些视觉模式大量出现，哪些能力是空白？
- 哪些案例值得进入 Studio 作为具体项目的对标证据？

## 11. 前端信息架构

| 路由 | 页面 | 作用 |
| --- | --- | --- |
| `/`、`/cases` | 案例库 | 浏览、搜索和多条件筛选 |

Case Hub 的 UI 应像专业的“科研视觉调研工作台”，而不是 Pinterest 式图片墙。来源、状态、分类、研究上下文和判断效率比纯视觉沉浸更重要。

# 第二部分：Sci AI Studio

## 14. 产品定位

Sci AI Studio 是面向科研视觉策划、摄影和宣传团队的“阶段式 AI 静图拍摄策划工作台”。它把用户上传或主动检索的真实资料、目标选择和 Case Hub 案例依据转化为：

- 可追溯的科研项目理解；
- 可追溯的科学与拍摄风险；
- 有案例依据的视觉策展策略；
- 可编辑的摄影方案与结构化画面卡；
- 可供科研人员审核的轻量页面；
- 可在拍摄现场使用的执行清单。

Studio 不是：

- 科研项目知识管理平台；
- 通用聊天机器人；
- 普通 AI 文案生成器；
- 一键生成漂亮 moodboard 的玩具；
- 替代科研人员确认事实的自动决策系统；
- 当前阶段的视频制作、脚本或后期管理工具。

MVP 只把“拍摄静图”做深。数据模型为视频保留扩展位，但 UI 中视频应明确为暂不可用。

## 15. 目标用户与协作角色

### 15.1 主用户

- 科研视觉策划、摄影、品牌或宣传团队；
- 需要快速理解陌生科研项目的人；
- 负责组织需求、设定目标、调整策略、制定拍摄方案并交付的人。

### 15.2 外部协作者

- 科研人员、实验室负责人、项目负责人或宣传接口人；
- 不需要注册完整 Studio 账号；
- 通过限时审核链接确认事实、保密、安全、可拍条件和关键表达；
- 审核意见进入待处理区，不会自动覆盖正式方案。

### 15.3 未来可能的管理角色

- 内测管理员：查看用户、配额、失败任务和反馈，但默认不应读取用户的原始私有资料。
- 当前管理后台仍属于后续工作，而不是已完成能力。

## 16. 用户要完成的核心闭环

```text
注册 / 登录
→ 创建一个科研静图项目
→ 上传、粘贴或通过 Fast / Deep Research 补充真实资料
→ 选择本次用于分析的资料
→ AI 理解科研项目、核心对象、已有事实与信息缺口
→ 用户确定主目标、受众和可选次目标
→ AI 形成科研视觉策略，并使用贯穿式 Case Hub 候选作为案例依据
→ AI 生成静图拍摄方案、画面卡和执行清单
→ 科研审校员持续检查事实、保密、安全和可拍性
→ 用户编辑、保存和查看版本
→ 发出限时审核链接
→ 处理科研人员反馈
→ 在现场按执行清单标记已拍 / 补拍并记录文件编号
→ 导出对外沟通版和摄影师执行版（导出管道仍待实现）
```

产品的价值判断标准不是生成了多少文字，而是用户是否能在较短时间内回答：

1. 这个团队有什么值得被看见？
2. 现有视觉缺什么？
3. 本次最重要的传播目标是什么？
4. 参考哪些真实案例，为什么？
5. 具体要拍哪些画面？
6. 每张画面如何执行，有什么风险？
7. 哪些事实必须由科研人员确认？

## 17. 固定工作流与阶段门槛

最新确认的默认流程有 7 个按顺序推进的节点：

1. **资料输入**：上传、粘贴、加入网页资料，或主动使用 Fast / Deep Research 补充公开来源。
2. **项目理解**：只理解项目背景、研究方向、核心对象、事实、限制与信息缺口，不作任何拍摄判断。
3. **目标与受众确认**：选择主目标、可选次目标和主要受众；产物为静图。
4. **科研视觉策略**：首次开始拍摄相关判断，形成视觉路线、核心表达和策略依据。
5. **静图拍摄方案**：把策略转为拍摄主题、场景组织和执行方法。
6. **画面卡与执行清单**：形成结构化画面卡、优先级和现场执行项。
7. **方案输出**：汇总策划提案、案例依据和摄影师执行版本。

Case Hub 不再是强制独立节点，而是 02–06 均可调用的案例证据层；04 是使用最集中的阶段。候选案例由系统自动建议，用户采用后才进入正式产物。AI 参考图作为方案阶段的可选能力，不再占用默认主流程节点。

节点不是自由拖拽的白板积木。React Flow 负责呈现、选择、缩放和上下文，不直接改变业务拓扑；业务状态由稳定节点 ID、模板版本、推进规则和持久化状态控制。

关键闸门：

- 资料较少时可以完成初步项目理解，但必须明确资料支持范围、未知和待确认问题；
- 未确定主目标，不能生成无焦点方案；
- 不再以 Case Hub 案例数量阻塞主流程；
- 阻塞级事实、保密、安全或可拍条件未解决，方案可预览但不能标记“可执行”；
- 至少要有一张 `MUST` 画面卡才能标记方案可执行；
- Agent 不应静默覆盖用户修改，而应创建新版本或局部建议。

## 18. 四个可见 AI 角色

四个 Agent 是清晰的工作角色，不必对应四个不同模型。

| 角色 | 主要职责 | 明确不负责 |
| --- | --- | --- |
| 资料分析师 `SOURCE_ANALYST` | 阅读用户资料与被采用的网络来源，理解项目背景、研究方向、核心对象、事实和信息缺口 | 拍摄判断、视觉路线、现有资产质量审计和完整拍摄执行 |
| 科研审校员 `SCIENCE_REVIEWER` | 贯穿检查事实、保密、安全、公开边界和可拍条件 | 代替科研人员确认；把未知事实写成确定事实 |
| 科研策展人 `RESEARCH_CURATOR` | 结合目标与 Case Hub 选择对标、解释借鉴关系、形成视觉路线 | 具体机位和现场执行；科学事实裁决 |
| 摄影策划师 `PHOTO_PLANNER` | 把策展 brief 转为主题、画面卡、拍摄建议和执行清单 | 改写已确认科研事实；当前阶段生成视频脚本 |

四角色的共同输出规则：

- 每条核心判断应有来源、待确认或用户补充三者之一；
- 证据带有置信度；
- 输出必须通过 Zod Schema，非法结构不能写入正式产物；
- 科研审校员会对诊断、策展、拍摄方案和最终汇总执行贯穿式二次检查；
- 失败必须显示为失败，不得偷偷回退成看似真实的 Mock 结果。

## 19. 项目目标模型

当前支持四类目标：

- 学术传播 `ACADEMIC_COMMUNICATION`；
- 公众传播 `PUBLIC_COMMUNICATION`；
- 招聘与团队品牌 `RECRUITING_BRAND`；
- 产业合作与转化 `INDUSTRY_COLLABORATION`。

每个项目选择 1 个主目标，最多 1 个次目标。这个限制是产品策略的一部分：避免一个拍摄方案同时试图服务所有受众，最终变成没有优先级的“大而全清单”。

## 20. 资料输入与解析

Studio 接受用户主动提供的：

- PDF；
- DOCX；
- PNG / JPG；
- 粘贴文字；
- 公开网页 URL。

资料输入还提供两种用户主动启动的联网资料收集方式：

- **Fast Research**：快速返回公开来源候选，用户选择后才加入资料池；
- **Deep Research**：后台异步生成结构化来源报告，不阻塞主流程，用户采用后才影响项目资料和后续版本。

不加入 Google Drive 或其他云盘，不做登录态网页采集、无边界递归爬取或自动采用全部搜索结果。用户始终决定哪些资料进入项目、哪些被选中供 Agent 使用。

资料状态包括：上传中、排队、解析中、摘要中、就绪、无摘要就绪、失败。系统保存原文、提取文本、OCR、图片描述、AI 摘要、模型信息、哈希、截断和错误状态。

解析策略：

- PDF：提取文本；扫描型 PDF 使用 OCR。
- DOCX：服务端提取正文。
- 图片：校验 MIME 和尺寸，生成安全预览，通过 Qwen 获取 OCR、客观描述和摘要。
- 文字：直接保存并可生成摘要。
- 网页：规范化 URL，做私网与 SSRF 检查，抓取公开正文并保留来源。

本地文件存储和生产 OSS 通过同一接口隔离；本地元数据可使用 JSON repository，生产使用 PostgreSQL。

## 21. Case Hub 贯穿式案例证据

Studio 通过 Case Hub 的 `/api/studio/recommendations` 类只读服务接口请求推荐，使用服务间密钥鉴权。案例能力贯穿 02–06，不再要求用户完成一个独立、强制的案例对标节点。

推荐输入包括：

- 学科或研究方向；
- 团队类型；
- 主/次传播目标；
- 偏好的技术手段；
- 固定媒介条件“静图”；
- 返回数量。

每个推荐返回：案例 ID、标题、缩略图、来源 URL 与域名、学科、三轴标签、内容类型、匹配分数、匹配层级、推荐理由和可借鉴点。

匹配层级：

- `EXACT`：方向、目标和条件高度匹配；
- `RELATED`：相关团队类型、学科或目标；
- `CROSS_DOMAIN`：跨领域但视觉策略有借鉴价值。

如果精确案例不足，必须显示降级匹配说明，而不是伪装成同类案例。系统可按阶段自动提供候选，用户可以选择、移除、替换案例；只有被采用的案例进入正式策略、方案或画面卡。没有案例或 Case Hub 暂时不可用时不阻塞主流程，但应显示证据缺口。

## 22. 策略、方案、画面卡与现场执行

Studio 的正式方案不是一整块 Markdown。结构化 `PlanDocument` 包含：

- 执行摘要；
- 目标；
- 视觉诊断；
- 对标总结；
- 策展策略；
- 拍摄方法；
- 风险；
- 来源引用。

每张 `ShotCard` 必须尽量回答“拍什么、为什么拍、怎么拍、有什么风险”，字段包括：

- 标题、表达目的、主体和场景；
- 人物 / 设备 / 材料；
- 景别、机位、构图；
- 光线、色调、动作；
- 科学信息；
- 优先级 `MUST / SHOULD / OPTIONAL`；
- 风险；
- Case Hub 参考案例和参考图；
- 排序与修订号。

现场 `CaptureItem` 将画面卡变成执行项，支持：

- 未拍 `TODO`；
- 已拍 `CAPTURED`；
- 需补拍 `RESHOOT`；
- 文件编号；
- 现场备注；
- 弱网重试和冲突提示。

## 23. 风险与“可执行”规则

风险分为：

- 科学事实 `FACT`；
- 保密 `CONFIDENTIALITY`；
- 安全 `SAFETY`；
- 可拍性 `SHOOTABILITY`。

严重度分为 `BLOCKER / WARNING / INFO`。只有阻塞风险得到明确解决、并且存在至少一张必拍画面卡时，方案才可标记为可执行。

“可执行”不是一句 AI 评价，而是可测试的业务规则。科学未知、禁拍区域、危险设备、敏感样品、尚未确认的公开边界都必须在方案中显式存在。

## 24. 版本、并发与后台任务

Studio 已建立：

- 多项目 CRUD 与软归档；
- 工作流 revision 和乐观锁；
- 当前方案与不可变历史版本；
- 恢复历史时创建新版本，而不是删除后续历史；
- 画面卡与执行项的独立 revision；
- 持久化 Agent Job；
- 幂等键、原子领取、有限重试、错误分类和进程恢复；
- 可配置 Worker 并发与用户每日 AI 配额。

Agent Job 状态主要包括排队、运行、完成、失败和取消；业务节点还包含锁定、就绪、等待人工确认等状态。UI 需要明确展示任务是否正在运行、失败是否可重试、使用了哪些资料和产生了哪个版本。

## 25. 外部审核

项目所有者可以创建限时、可撤销的审核链接：

- Token 原文只在创建时返回；服务端只保存不可逆哈希；
- 可设置有效期；
- 支持撤销、过期、篡改和重复提交处理；
- 公开快照只包含审核所需的最小方案内容；
- 不泄露私有来源 ID、内部参考案例 ID、对象存储路径或其他项目数据；
- 科研人员可确认、请求修改或留言；
- 审核意见形成待处理记录，由项目用户采纳、忽略或处理，不直接覆盖方案；
- 操作进入审计记录。

## 26. 身份、配额和数据隔离

- 本地开发默认可使用 Mock Auth。
- 线上使用 Clerk 邮箱和密码注册、验证、登录、退出与重置密码。
- 每个项目、资料、工作流、方案、Agent Job 和用量都归属于认证用户。
- 服务端再次校验资源归属，不能只依赖前端隐藏。
- 默认配置：每用户最多 50 份资料、500 MB 存储、每日 50 次 AI 任务；都应由环境变量调整，不写死内测人数。
- API 有基础限流。
- 生产环境缺少 Clerk 或隔离密钥时应拒绝启动。

## 27. AI 与模型服务

当前模型边界：

- DeepSeek：四个工作角色的结构化文本任务；可切换 Mock Gateway 用于确定性开发和测试。
- Qwen / DashScope：图片 OCR、图片描述、文档或网页摘要；OpenRouter 可作为回退。
- OpenRouter 图像模型：可选的 AI 参考图生成。

所有密钥只存在于服务端环境变量，不进入前端、共享契约、提示词或 Git。Agent 角色与模型供应商解耦，未来可以更换或按任务路由模型，而不改变用户理解的四个角色。

AI 参考图只用于沟通画面方向，不是科研证据，不应冒充真实实验结果，也不能替代真实拍摄。

## 28. Studio 信息架构与界面

当前代码中的主要路由：

| 路由 | 页面 |
| --- | --- |
| `/` | 项目列表、新建、重命名与归档 |
| `/projects/:projectId` | Studio 固定流程画布与右侧上下文面板 |
| `/help` | 帮助中心 |
| `/review/:token` | 免登录外部审核页 |

Studio 的桌面布局是“顶部项目栏 + 中央流程画布 + 右侧上下文面板”。现场清单和审核页需要兼容窄屏。视觉系统以黑、白和 `#2569ED` 蓝为核心，强调专业、克制、清楚的科研工作台感，而不是聊天窗口或炫技式 AI 控制台。

当前 UI 将诊断、对标、策略、方案、审核和执行等功能嵌入流程节点及上下文面板，并非最初设计文档中每个阶段都对应独立路由。Brainstorm 新导航时要先判断是扩展现有画布，还是引入可深链的详情页。

# 第三部分：两个产品如何形成闭环

## 31. 数据与决策流

```text
[外部公开视觉世界]
高校 / 实验室 / 期刊 / 科研机构 / 企业研发
                    │
                    ▼
          Sci-Viz Case Hub
采集 → 资产保存 → OCR/AI → 三轴编码 → 人工复核
                    │
                    ├── 分布与跨源研究
                    ├── 风格谱系与方法论
                    └── 受保护的案例推荐
                                  │
                                  ▼
                         Sci AI Studio
用户私有资料 → 项目诊断 → 目标 → 对标 → 策展 → 拍摄方案
                                  │
                       科学审校与人工确认贯穿
                                  │
                                  ▼
               画面卡 / 审核页 / 现场清单 / 最终交付
```

Case Hub 提供的是“参照和证据”，不是替 Studio 做最终策略；Studio 提供的是“项目化决策与执行”，不是替 Case Hub 做长期研究。

## 32. 推荐逻辑的产品意义

推荐不是“找长得像的图”，而是多层匹配：

- 科研方向是否相关；
- 团队或机构类型是否相近；
- 传播目标是否一致；
- 功能维度是否能解决当前视觉短板；
- 技术手段是否在现场可实现；
- 媒介是否符合当前静图项目；
- 案例来源是否可信、是否有可解释的借鉴点。

未来可以引入视觉 embedding、语义检索和人工策展权重，但不能牺牲来源追溯、匹配解释和三轴口径。

## 33. 未来反馈闭环

当前尚未正式实现，但很有战略价值的闭环是：

```text
Case Hub 中的参照案例
→ Studio 中被选择、被移除、被实际采用
→ 方案与拍摄执行结果
→ 哪些画面完成、补拍或放弃
→ 人工评价策略是否有效
→ 反向改进推荐权重、分类词典和采集优先级
```

这里必须区分公共案例数据与用户私有项目数据。任何反向学习、统计或产品分析都要先设计隐私、匿名化、用户授权与数据保留边界。

# 第四部分：产品原则、约束与 Brainstorm 边界

## 34. 不应被轻易改变的产品原则

1. **研究先于生成。** Studio 的优势来自 Case Hub 的真实研究资产，不应退化成通用大模型套壳。
2. **证据先于断言。** 科研事实必须有来源、待确认或用户补充标记。
3. **人拥有最终决定。** AI 提议，用户选择，科研人员确认关键事实与风险。
4. **策略必须落到执行。** 每个宏观概念最终应能转化成具体画面、对象、机位、光线、动作和现场条件。
5. **三轴口径保持纯净。** 不把题材、学科、旧字段或采集方式混入三轴结论。
6. **公共参照与私有项目隔离。** Studio 不直连 Case Hub 数据库；用户数据不回流为公共案例，除非有明确授权。
7. **状态必须真实。** 失败、Mock、降级匹配、待确认、未部署验证都要明确展示。
8. **先做好静图闭环。** 视频是未来方向，但当前不能为了扩品类稀释静图策划深度。
9. **内部研究工具与用户产品采用不同基础设施。** Case Hub 保持合适的 SQLite 内部工作台架构；Studio 按多用户产品设计 PostgreSQL、认证、隔离和配额。
10. **设计服务于判断。** UI 要让来源、状态、风险、选择和下一步清楚，而不是用视觉效果掩盖信息结构。

## 35. 常见错误理解

- 错：Case Hub 是 Studio 的素材文件夹。  
  对：它是可持续扩展、可编码、可研究、可解释推荐的视觉证据基础设施。

- 错：Studio 的四个 Agent 就是四个聊天机器人。  
  对：它们是固定工作流中职责不同、输入输出受 Schema 约束的业务角色。

- 错：AI 生成的建议可以直接成为可执行方案。  
  对：还需目标与受众确认、风险检查、人工编辑、科研审核和可执行规则；Case Hub 案例用于增强依据，但不再是强制闸门。

- 错：图片是浏览器截图，所以技术手段是截图。  
  对：截图只是采集方式；技术手段描述原视觉如何被生产。

- 错：`mediaType` 就是媒介维度。  
  对：它是历史混合字段；媒介维度必须使用 `distributionMedium`。

- 错：Studio 已经是可公开收费的完整 SaaS。  
  对：它正处于稳定内测准备阶段，核心闭环大量实现，但导出、管理、生产验证、安全运维仍有缺口。

- 错：Case Hub 当前数据库数量可以写进永久产品介绍。  
  对：数量持续变化，只能动态查询或写量级。

## 36. 适合继续 Brainstorm 的方向

### Case Hub

- 如何从“分类数据库”升级为真正的视觉谱系与模式发现工具；
- 三轴频谱、时间变化、来源差异和学科差异的可视化；
- 人工抽检、标注一致性和不确定性表达；
- 多模态相似检索与可解释推荐；
- 企业商业化视觉与学术视觉之间的转译框架；
- 动图、视频、交互与实体媒介的采集和研究方法；
- 失效网页、版权、来源快照和长期资产保存策略。

### Sci AI Studio

- 如何让第一次使用者在 15–30 分钟内真正得到价值；
- 资料不足时怎样提出高价值、低负担的追问；
- 诊断、对标、策略、画面卡之间如何保持来源链；
- 如何评价推荐是否真的帮助了最终拍摄；
- 画面卡的批量编辑、场景分组、拍摄日程和资源安排；
- 科研人员审核如何更快、更准确，而不是变成另一套复杂后台；
- 导出、客户沟通、现场执行三种信息密度如何分别设计；
- 是否以及何时扩展到视频、动画、科学插画或整体视觉项目；
- 如何建立内测反馈、输出质量评估和运营指标。

### 双产品系统

- Studio 选择行为是否可以匿名反馈推荐质量；
- Case Hub 的研究结论如何成为 Studio 的可操作规则，而不只是案例列表；
- 一个 Studio 项目的最终成果在什么授权条件下可以回到 Case Hub；
- 如何把“三轴 + 学科 + 目标 + 场景 + 可拍性”转成统一检索与推荐模型；
- 如何形成科研视觉行业的 benchmark、能力地图和方法论标准。

## 37. Brainstorm 时建议先回答的问题

任何新功能提案最好先回答：

1. 它服务 Case Hub 的“研究证据”还是 Studio 的“项目决策”？
2. 谁是直接用户，发生在工作流哪个阶段？
3. 输入来自哪里，是否可信、可追溯、可长期保存？
4. 输出是建议、正式产物还是执行状态？
5. 哪一步必须由人确认？
6. 是否会混淆三轴、题材、学科和采集方式？
7. 是否会让 Studio 越过科学事实、隐私或安全边界？
8. 是否能落到画面卡或明确的研究结论，而不是只增加文字？
9. 需要修改哪个产品，还是只需通过 API 连接？
10. 现在是内测必须项、验证性实验，还是远期方向？

## 39. 开始工作前的事实核验建议

新 AI 不应只读本文件就直接修改核心逻辑。建议按任务类型核验：

- 产品 brainstorm：本文件 + MVP 设计 + beta roadmap。
- 三轴分析：AGENTS.md + 三轴词典 + 实时数据库统计。
- Case Hub 功能：实际路由、前端页面和 schema。
- Studio 功能状态：当前代码、测试和 roadmap 顶部进度。
- 数据数量：实时查询 SQLite，不引用旧文档。
- 生产能力：检查环境配置、部署文件和真实环境验收记录，不把“有代码”写成“已生产验证”。
- 修改前先检查 Git 状态；当前工作区可能有用户尚未提交的修改，必须保留并避免覆盖。

## 40. 建议 AI 在 Brainstorm 中采用的输出结构

```text
问题 / 机会
→ 目标用户与使用时刻
→ 为什么属于 Case Hub 或 Studio
→ 核心假设
→ 最小用户流程
→ 数据与 AI 输入输出
→ 人工确认点与风险
→ 与现有架构的连接方式
→ 成功指标
→ MVP / 后续 / 不做
→ 需要验证的问题
```

这样可以避免 brainstorm 只产生功能清单，而能形成与现有产品方向一致、可验证、可实现的产品假设。

## 结语

这套产品的独特性不在“AI + 科研 + 图片”三个词的组合，而在于它试图把三种通常割裂的能力接起来：

1. 对科研视觉世界进行长期、结构化、可比较的观察；
2. 对一个具体科研项目进行有来源、有边界的理解与视觉判断；
3. 把判断转化为摄影团队和科研人员都能讨论、确认并执行的画面方案。

一句话概括：

> **Sci-Viz Case Hub 负责让系统“见过并研究过足够多的科研视觉”，Sci AI Studio 负责把这种见识转化为一个真实科研项目下一次应该如何被看见。**
